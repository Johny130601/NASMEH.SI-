# Phase 3 repair and acceptance record — 2026-09-09

The user authorized the five repair steps identified in the [independent audit](phase-3-audit-2026-09-09.md). This record separates the repaired implementation and local verification from the still-required [real-provider sandbox acceptance](phase-3-sandbox-checklist.md).

## Repairs implemented

1. **Private orders and safe post-purchase actions.** Confirmation requires the owning account, an admin session, or a signed HttpOnly purchaser receipt. Order numbers alone grant no access. Creating a post-purchase account requires that receipt, cannot take over an existing email, and follows the existing Phase 5 email-verification flow. Automatic cart clearing is limited to one paid-order visit and the original unchanged cart/principal/version; later carts survive revisits and payment delays.
2. **Atomic payment and stock transitions.** Verified events, order state, invoice identity, timeline and inventory changes commit together. Order and sorted variant locks prevent repeat deductions and competing orders from overselling. Bundle components and standalone quantities are aggregated. Unknown orders and monetary mismatches remain retryable. A captured payment that cannot be fulfilled records the amount received and an explicit refund obligation. Partial and full refunds do not repeat inventory deductions or revive completed orders.
3. **Cart, totals, invoices and packaging.** Signed-in additions increment atomically and respect purchase caps. The checkout summary and review use a signed server quote covering items, delivery, coupon, VAT and total; stale quotes require another review. Shipping destinations come from configured methods and postal validation follows the selected country. Coupon rejection and terms stay visible. Invoice PDFs include discounts and Slovenian characters. Demo users are verified without overwriting passwords. Docker includes seeded placeholder media and persists uploads in a named volume.
4. **Provider UI and recovery.** Stripe Payment Element and PayPal buttons use server-created provider objects. PayPal capture and official webhook verification are implemented; approval alone never marks an order paid. Provider requests happen outside the order transaction with stable idempotency keys. An owned pending confirmation can resume the existing attempt, including after a timeout or browser exit. Captured/processing provider states wait for verified webhooks. Amount/currency mismatch suppresses payment controls. Turnstile renders and verifies real tokens, handles expiry, and bounds verification requests. Order confirmation delivery has a durable pending flag, lease and retry path.
5. **Acceptance coverage.** Added regression tests for access, account claiming, cart concurrency, combined bundle inventory, competing payments, transaction rollback/replay, cancellation, refunds, exact checkout quotes, stale prices, provider recovery and verification. Final local verification results are recorded below after the complete run.

Klarna remains disabled by default. Product, cart, sticky-bar and footer installment claims now follow `STRIPE_KLARNA_ENABLED`; this follows the master plan's existing requirement to confirm SI buyer eligibility before launch. The sandbox checklist includes official provider sources and the eligibility gate.

## Remaining gates

Real Stripe, PayPal and Turnstile acceptance has **not** been executed: their credentials are absent from local `.env`. The implementation and local mocks do not establish real 3DS, wallets, PayPal approval/capture, provider webhook delivery or dashboard reconciliation. Complete the [sandbox checklist](phase-3-sandbox-checklist.md) with test credentials before marking Phase 3 accepted. Keep secrets in local environment configuration, not in chat or source control.

Deployment must schedule the authenticated daily job to retry queued confirmation mail. SMTP delivery is at-least-once: a process crash after SMTP accepts a message but before the sent marker commits may cause another delivery. A stable Message-ID helps downstream deduplication but cannot guarantee it. Captured stockout/cancelled orders require an operator refund; this repair records that obligation rather than issuing an unreviewed refund automatically.

`npm audit` reports 11 advisories (8 high, 3 moderate) in existing dependencies. The affected installed package versions are unchanged from HEAD; the new Stripe/PayPal UI dependencies are not listed. Dependency remediation remains a release-hardening item and is not certified by the functional tests.
