# Phase 6, step 3 — Public order tracking

**Date:** 2026-09-09. **Status:** step 3 complete and locally verified on this Windows workstation (see the [build-and-verify record](build-verify-2026-09-09.md) for the environment). Steps 4–6 have not started.

## Delivered behaviour

- **Fulfilment transitions** in `lib/orders/transitions.ts`: `markOrderShipped` (PAID/PROCESSING → SHIPPED) requires a carrier that a configured shipping method uses and a tracking number that normalises to `[A-Z0-9-]{6,40}`; it stores the normalised number, stamps `shippedAt` once, appends a `shipped carrier:actor` timeline entry and queues the shipped email. `markOrderDelivered` (SHIPPED → DELIVERED) appends `delivered actor`; the existing database trigger stamps `deliveredAt`. Both lock the order row, return typed results (`not_found`, `invalid_transition`, `missing_tracking`, `unknown_carrier`) and never throw for expected cases. There is no admin screen yet: Phase 7 step 2 adds it on top of these functions.
- **Shipped email** (`lib/email/templates/order-shipped.ts`): carrier, number, the carrier link from `lib/tracking.ts`, the delivery estimate of the snapshotted shipping method and a button to `/sledi?sledenje=<number>`. Delivery is durable (`lib/orders/shipped-delivery.ts`): pending flag, five-minute lease, attempts and last error type on the order, post-commit send, and a `shippedRetries` stream in `POST /api/jobs/daily` (503 on real failures, skips for held leases).
- **Public tracking page** `/sledi`: tracking-number mode returns status, carrier, carrier link, ship date and estimate only; e-mail + order-number mode adds order number, method, item count, total and order date. Every lookup passes the Turnstile guard and a per-client, per-mode rate limit of 20 per 10 minutes whose overflow reads exactly like a miss. Links from the shipped email and the account only prefill the forms. Page stays `noindex`. The old GET lookup (`LookupForm`, `lookupOrderAction`) is removed.
- **One carrier-link source**: the account order detail, the shipped email and the tracking page all derive the link through `trackingUrl()`; the browser test asserts the three hrefs are identical.
- **Migration 14** `20260909190000_phase6_tracking`: `Order.shippedAt`, the four `shippedEmail*` columns, an index on `trackingNumber`, and a one-time backfill of `shippedAt` from `deliveredAt`/`updatedAt` for legacy shipped/delivered rows.
- Deviation from the design: browser tests call `markOrderShipped`/`markOrderDelivered` directly (the existing cart-persistence pattern) instead of a test-only Server Action, so no test hook ships in the app.

## Operations notes

- The host job that invokes `/api/jobs/daily` now also drains queued shipped notifications; its JSON gains `shippedRetries` with the usual `{processed, sent, failed, skipped}` shape.
- Until Phase 7 step 2, orders are shipped by calling `markOrderShipped` (for example from a maintenance script); the carrier must match a `shipping.methods` carrier (seed: `Pošta Slovenije`, `GLS`) and the tracking templates in `tracking.templates` decide whether a link is rendered.
- The rate limiter is in-process (single container), keyed by `x-forwarded-for`; the reverse proxy must set that header truthfully in production (existing Phase 3 note for the email check applies).
