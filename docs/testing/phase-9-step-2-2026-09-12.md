# Phase 9 step 2 — performance: acceptance record (2026-09-12)

Plan: [docs/plans/phase-9.md](../plans/phase-9.md) step 2 design. Budgets: LCP < 2.5 s, TBT < 200 ms (lab proxy for INP), CLS < 0.1, performance ≥ 90 desktop and ≥ 80 mobile on the four templates (home, product page, cart, checkout). Everything below ran on this workstation against the standalone production build on 127.0.0.1:4317 (fresh database `nasmeh_phase9_step2_20260912`); Lighthouse's own simulated throttling (mobile: slow 4G, 4× CPU slowdown) supplies the network and CPU conditions, so the numbers are lab numbers, comparable run to run, not field numbers.

## Delivered behaviour

- **Lighthouse CI tooling** (`@lhci/cli` dev dependency, `scripts/lighthouse/`): `npm run lighthouse` collects three runs per template on desktop and on mobile against a running standalone server (`LH_BASE_URL` for any other deployment), asserts the budgets on the **median** of the runs, writes the reports under `docs/testing/lighthouse/<dir>/<device>/` and a Markdown summary (`summary.cjs`). `cart-cookie.ts` signs a guest cart with one seeded unit so `/cart` and `/checkout` measure with a line in the cart. The bulky per-run reports are git-ignored; `manifest.json` and `summary.md` are committed.
- **Fonts:** one Slovenian-Latin subset of Plus Jakarta Sans (`jakarta-sl.woff2`, 38 kB: Latin-1, Latin Extended-A with č š ž đ ć, general punctuation, €; built with fontTools from the upstream variable font with the weight axis instanced to the 300–800 the CSS declares) replaces the two Google subsets the pages needed (latin + latin-ext, 49 kB, two requests) and the two they never referenced (Cyrillic-ext, Vietnamese); the root layout preloads it with an explicit `<link rel="preload">` (`ReactDOM.preload` from the layout emitted nothing into the built HTML), and `/fonts/*` is served `Cache-Control: public, max-age=31536000, immutable` (Next.js gives `public/` files `max-age=0`; only its hashed chunks were immutable). The committed placeholder artwork under `/uploads/placeholder-*` is cached for a day until the real media (gate D2) arrives through the media library, which serves its files immutable already.
- **Images:** the hero poster carries `fetchpriority="high"`; the catalog banner declares its intrinsic sizes on both sources so its box exists before the artwork arrives; on the product page the second gallery image loads eagerly (it enters the first mobile viewport and was the lazy-loaded LCP), the first keeps `fetchpriority="high"`, the rest stay lazy. Product and card images are the media library's single WebP (≤ 1600 px, quality 85); responsive `srcset` variants are not generated — recorded as backlog **B16** (see below), not needed for the budgets.
- **JavaScript:** Stripe.js (250 kB, plus its fraud beacon) no longer loads on the first checkout step: the payment panel imports `@stripe/stripe-js/pure`, so the script loads when `loadStripe` runs at the payment step with a key. The checkout's own bundle lost two passengers: zod (20 kB gzipped) rode in through `lib/orders/checkout-schema`, which the wizard and the account address book imported for the country list and the postal-code helper — those now live in the zod-free `lib/orders/checkout-constants.ts` (re-exported by the schema module for server code); and the payment panel with the Stripe and PayPal React bindings (14 kB gzipped) is a `next/dynamic` import that loads when an order has been placed (checkout) or a payment is resumed (account). Route bundles before: shared first load 106 kB; home 135 kB, product page 136 kB, cart 136 kB, checkout 170 kB; after: shared 106 kB, home 135 kB, product page 136 kB, cart 136 kB unchanged, **checkout 140 kB** and the account data page 135 kB (from 155 kB; the address book imported the same schema module). The Phase 7 editors are admin-only and outside the storefront budget.
- **Favicon:** `app/icon.svg` (brand mark) — every page logged a `favicon.ico` 404 in the console before, which Lighthouse counts against best practices.
- **Accessibility defects the runs surfaced, fixed:** the marquee text is `text-dark-1` on the brand bar (white on brand measures 3.0:1 at 14 px, short of WCAG AA's 4.5:1) and the marquee link carries the announcement as its accessible name (its visible track is `aria-hidden`); the header cart link's name includes the visible badge count (WCAG 2.5.3 label-in-name); the free-shipping progress bar is labelled by its status sentence.
- **Structured data:** the product JSON-LD carries `sku` (Google's recommended field) next to brand and offer.
- **Caching decision (recorded, not built):** the storefront routes stay `force-dynamic` — they read settings, menus, consent and the cart per request. The product page is the ISR candidate (catalog and price rows change through the admin only), but with TTFB ≈ 0.45 s in the lab and the budgets met on three of the four templates (the product page misses by 1 %, deviation 3), ISR is deferred until the re-measurement with real media or field data asks for it; when it comes, `revalidateTag` calls belong in the catalog write paths (`lib/admin/*`) and the prices must keep their Omnibus history.

## Backlog added

- **B16** — responsive image variants: the media library stores one WebP per upload (≤ 1600 px). Serving `srcset` widths (e.g. 480/960/1600) for cards and the hero needs variant generation at upload, storage of the variant names and a re-encode of existing media; not needed for the budgets with the current markup (cards are 240–272 px wide and lazy), revisit with real media after gate D2.

## Deviations from the step 2 design

1. **WebP/AVIF with `srcset`** for the hero and cards is not delivered (B16 above); the images are WebP through the media library and the placeholders are SVG.
2. **Results committed** as `manifest.json` + `summary.md` per run directory; the full HTML/JSON reports (≈ 0.5–1 MB each, 24 per run) are git-ignored.
3. **Mobile LCP on the product page: 2.53 s against the 2.5 s budget** (1 %, identical across the three runs; the other three templates pass). The budget assertion stays strict — `npm run lighthouse` reports the miss until it is gone. The measured element is a placeholder SVG the browser only picks because the real hero slot holds artwork with no visual entropy; re-measure after gate D2 with real media, and if the product page still misses, build the ISR path recorded above (it removes the 0.45 s simulated TTFB from the critical path).

## Operations notes

- `npm run lighthouse` needs a running standalone server (`npm run build && npm run start` with the Playwright environment) or `LH_BASE_URL=https://…` for the deployed site, Chrome installed, and optionally `LH_CART_COOKIE` from `scripts/lighthouse/cart-cookie.ts` (needs `DATABASE_URL` and the server's `AUTH_SECRET`). Reports go to `docs/testing/lighthouse/latest/` unless `LH_OUTPUT_DIR` says otherwise.
- The SEO category on `/cart` and `/checkout` stays low by design (`noindex`); the best-practices category on the checkout reflects Stripe's third-party cookie once the payment step loads Stripe.js.
- Field data (CrUX, or the analytics vendor's Web Vitals) is the go-live measure (gate G4); the lab budgets here are the regression fence.
