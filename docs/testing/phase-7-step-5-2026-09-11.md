## Findings fixed during the step

| # | Finding | Resolution |
|---|---|---|
| F1 | `deletePageAction` would delete the cookie-policy, withdrawal and complaints pages that static routes render inside their own templates (the routes would then 404 their content) | The action refuses those slugs with `protected`, the editor hides the delete button for them and explains that unpublishing is the way to hide them |
| F2 | The popup screen promised that the code "must exist among coupons" but never checked; a typo would have auto-applied a code the cart rejects | `savePopupAction` looks the code up and refuses inactive or unknown codes with a dedicated message |
| F3 | The plan's P1 list names "withdrawal received"; the receipt the withdrawal, complaint and contact forms send bypassed the override path | `supportReceipt` joins the template keys (reference and statutory note placeholders); `lib/support/delivery.ts` resolves the customer receipt through the same `resolveMail` as every other customer mail |
| F4 | The hero's code fallback CTA (`#izdelki`) was not representable in the form: the link schema refused same-page anchors, so the editor defaulted to `/trgovina` | `linkSchema` accepts `#anchor` links; the editor defaults to the same anchor as the storefront |

## Deviations from the step 5 design

1. **E-mail keys.** "Payment failed" has no mail at P1 — Phase 3 shows the failure in the checkout and offers to resume payment — so there is nothing to template. "Welcome (+code)" is the double opt-in mail (`verifySubscription`); the code itself is shown in the popup's thank-you state and auto-applied at checkout. "Withdrawal received/confirmed" is the support receipt (`supportReceipt`), which covers every ticket kind through the `note` placeholder. Staff notification mails stay code-only (internal, carry private links).
2. **Collection banners** keep the step 3 upload instead of the library: removing a banner deletes its file, which must never happen to a shared library file. The library serves the hero poster and routine banner (by `datalist`) and page bodies (by pasted path).
3. **Page preview** renders the saved body server-side (as designed) rather than live edits; the editor says so.
4. **Popup suppression rules** (cart, checkout, account, known subscribers, once per session) stay in code as the Phase 4 design specified; the form edits copy, code, delay and the switch.
5. **`MediaAsset` table** was not in the plan's migration list; the library needs alt text, dimensions and size per file to show references and to keep the storefront `<img>` alt attributes meaningful.

## Operations notes

- Placeholders are written as `{{name}}`; text values are escaped, prepared blocks (`items`) are inserted as they are and cannot be used in a subject. Reset returns a key to the code template; the list shows which keys are overridden.
- Library paths (`/uploads/media/knjiznica-medijev/…webp`) can be pasted into any page body or media field; a file in use cannot be deleted until the reference is replaced.
- Reserved slugs are the storefront's code routes; the three legal slugs with static routes can be edited (body, SEO, reviewed flag) but not deleted — unpublish to hide them.
- The marquee switch hides the bar without losing the text; menus are read on every request, so a broken link in the header is live immediately — use the preview link on the storefront after saving.
