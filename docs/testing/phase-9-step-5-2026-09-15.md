# Phase 9 step 5 — deployment, staging and cron: acceptance record (2026-09-15)

Plan: [docs/plans/phase-9.md](../plans/phase-9.md) step 5 design (gate **G3**, the host). The home server does not exist yet, so the step delivers everything the host will need and rehearses the whole deployment shape on this workstation (Windows 11, Docker Desktop 29.7.2, Git Bash): the production compose project and a staging project, both from **empty databases**, behind a TLS-terminating nginx on a shared docker network — the runbook's host section, executed. What only the host can prove (DNS, real certificates, the proxy already running there, cron on the host clock) stays open and is listed at the end.

## Delivered

- **The site URL is read at request time** (`lib/seo.ts` `siteUrl()` assembles the env key so the build cannot inline it). Before this step the image baked `http://localhost:3000` into the sitemap, canonicals, mail and coupon links (finding F1); now one image serves staging and production with their own `NEXT_PUBLIC_SITE_URL`, and the image can be built anywhere.
- **Loopback-only publishing and a proxy compose file.** `docker-compose.yml` publishes the app on `127.0.0.1:${PORT}` and pins the container's own `PORT=3000` / `HOSTNAME=0.0.0.0`; `docker-compose.proxy.yml` attaches the app to the host's proxy network (`PROXY_NETWORK`, default `proxy`) without editing the committed file on the server.
- **A fresh database is usable without the dev seed.** Migration `20260915100000_phase9_legal_pages_bootstrap` (27 migrations in total) inserts the five legal pages the seed alone used to write, only when missing, as published unreviewed drafts with the seed text (`tests/unit/legal-pages-bootstrap-migration.test.ts`); `lib/bootstrap/owner.ts`, called from `instrumentation.ts` on every start, creates the OWNER account from `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` when none exists, refuses the `.env.example` password in production, never promotes another account on the same address and logs no address (`tests/unit/bootstrap-owner.test.ts`, 6 cases). The checklist row LT-5 (legal texts reach production) is closed by this.
- **Runbook "Host" section** ([docs/RUNBOOK.md](../RUNBOOK.md)): prerequisites, the host `.env` table, first start of an empty database, the nginx server block and the Traefik labels that were rehearsed, staging as a second project with maintenance mode and the index switch, cron on the loopback URL; deploy commands with the proxy file. AGENTS.md §6 and `.env.example` updated to match; the phase plan's step 5 design corrected (request-time URL instead of a build-time value, proxy file instead of editing compose, first-start bootstrap).

## Findings fixed during the step

| # | Finding | Fix |
|---|---|---|
| F1 | **The image baked `http://localhost:3000` as the site URL.** `siteUrl()` read `process.env.NEXT_PUBLIC_SITE_URL` literally, which Next.js inlines at build time; the Docker build has no `.env`, so the sitemap, canonicals, OG URLs, mail links, coupon links and PDF links of a deployed store would all have pointed at localhost (verified on the compose stack before the change). The design's "bake it at build time" also contradicted "staging is the same image" | request-time read through an assembled key; only `/_not-found` and the icon are prerendered, neither carries an absolute URL |
| F2 | **A host `PORT` other than 3000 broke the container.** `env_file: .env` carries the whole host `.env` into the container, so `PORT=3001` (staging) made the standalone server listen on 3001 while the health check, the port mapping and the proxy expected 3000: the container came up unhealthy and nginx answered 502. Production had worked only because its `PORT` happened to be 3000 — the runbook's advice to pick a free host port would have broken it | `PORT: "3000"` and `HOSTNAME: 0.0.0.0` pinned in the compose `environment:` (the host `PORT` remains the published port only) |
| F3 | A fresh production database had no owner account and five legal pages missing (404 from the footer, checkout and the confirmation mail's links); the only way to get them was the dev seed with its demo catalogue | the bootstrap migration and the owner bootstrap (above) |
| F4 | Rehearsal harness: the browser script could not resolve Playwright from outside the repository, and two checks were wrong (the CSP header rides page responses, not the health JSON; the withdrawal PDF is 503 until the company data exists) | `file:///` import of the repository's Playwright; checks corrected, the PDF check now proves both states |

## Deviations from the step 5 design

1. **No host.** Everything ran on the workstation behind a self-signed nginx; DNS, Let's Encrypt, the proxy that already runs on the server, cron on the host clock and the uptime checker remain to be done there — the host section of the runbook is the script for it. The acceptance item "a checkout in test mode through the proxy" was not run: the rehearsal databases are empty (no catalogue), and the test-mode checkout is covered by the e2e suite on the standalone server; it is repeated on the host with the D2 catalogue (step 6 go-live list).
2. **Site URL at request time, not build time** (design change, F1).
3. **The proxy network is a second compose file**, not a block uncommented on the server (keeps the server checkout clean for `git pull`).
4. **Owner bootstrap on server start** rather than a one-off command: the runtime image bundles its dependencies into route chunks, so a standalone script could not load Prisma and bcrypt; the start-up hook runs after the entrypoint's migrations and is idempotent.
5. **Staging switches were written by SQL** in the rehearsal, standing in for the admin forms the operator uses.
