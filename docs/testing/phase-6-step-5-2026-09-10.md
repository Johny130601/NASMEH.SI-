# Phase 6, step 5 — Back-in-stock alerts

**Date:** 2026-09-10. **Status:** step 5 complete and locally verified on the Windows workstation of the [build-and-verify run](build-verify-2026-09-09.md), on top of commit `791b6a0` (step 4). Step 6 is in progress. Every number below was produced in this run.

## Delivered behaviour

- **Migration 16** `20260910100000_phase6_restock`: `BackInStockSubscription` gains `notifiedAt`, `alertPendingSince`, `alertLeaseUntil`, `alertLeaseToken`, `alertAttempts` and `alertLastError` plus the `(alertPendingSince, alertLeaseUntil)` index. `SubscriberStatus` is unchanged; a notified row stays `CONFIRMED`. Backlog B4 is closed.
- **Stock helper** `lib/inventory/stock.ts` (general plan rule 13): `setVariantStockInTx(tx, variantId, stock)` locks the variant with `FOR UPDATE`, writes the quantity only when it changes and, on a 0 → N transition, arms every `CONFIRMED`, un-notified, un-armed subscription for that variant or for the product without a variant, in the same transaction; it returns `{ before, after, armedAlerts }`. `adjustVariantStockInTx` applies a delta through the same path and refuses a negative result. Non-integer or negative quantities are rejected before any write. `deductOrderInventory` remains the only decrement path. The seed's variant update path now writes stock through the helper.
- **Operator entry point** `lib/inventory/restock.ts` `setVariantStock`: one transaction, then a best-effort `sendPendingRestockAlerts()` flush; a flush failure leaves the armed rows for the daily job.
- **Alert job** `lib/jobs/restock-alerts.ts` `sendPendingRestockAlerts(now, limit)`: selects armed, confirmed, un-notified rows whose lease is free (attempts ascending, oldest first, at most 100), claims each with a random lease token for five minutes and an attempt increment, re-reads the row with its product and variants, and sends only when the row is still `CONFIRMED` and un-notified, the product is `ACTIVE` and a variant has stock. Rows that sold out again or were withdrawn are disarmed and kept for the next restock. A successful send stamps `notifiedAt` and clears the queue fields under the lease token; a failure releases the lease and stores only the error name, never the recipient. Results use the `{processed, sent, failed, skipped}` shape as stream `restockAlerts` in `POST /api/jobs/daily`, which returns 503 when any stream reports a failure.
- **Alert email** `lib/email/templates/back-in-stock-alert.ts` and `sendBackInStockAlertEmail`: product title, VAT-inclusive price through `lib/pricing`, PDP link, one-click unsubscribe link, stable `Message-ID` per subscription; copy in `lib/copy/email.ts`.
- **Unsubscribe** `/odjava-zaloga/[token]`: the token is `<subscriptionId>.<HMAC-SHA256>` over the id with `AUTH_SECRET`, verified with a constant-time comparison after shape checks. A valid link sets `UNSUBSCRIBED`, clears the queue fields and writes one `ConsentLog` row (`kind: back-in-stock`, `unsubscribed: true`, product slug); repeated visits change nothing; a tampered link renders the invalid-link page. `noindex`, server-rendered.
- **Re-subscribe semantics** in `subscribeBackInStockAction`: a `CONFIRMED` un-notified address is a no-op success with the "already active" message; a `CONFIRMED` notified address is re-armed by clearing `notifiedAt` and the queue fields without a new confirmation mail; a `PENDING` address gets a fresh confirmation token as before.
- **Copy**: `lib/copy/backInStock.ts` (`alreadyActive`, `unsubscribe`), `lib/copy/email.ts` (`backInStockAlert`).

## Deviations from the step 5 design

1. No test-mode `testSetStockAction` ships. The browser spec calls `setVariantStock` directly (the step 3 pattern) and seeds a `CONFIRMED` row instead of driving the PDP → confirmation email → restock chain; the PDP dialog path is covered by the second case, and the double opt-in itself is covered by `pdp.spec.ts`.
2. A tampered unsubscribe link renders "Povezava ni veljavna" with HTTP 200, the contract of `/potrdi-zalogo` and `/potrdi`, rather than the 400 the general plan lists; the 400 rule was written for the rating-token form POST.
3. The helper takes positional arguments without the design's `reason` label: no audit table consumes it at P1. Phase 7 step 3 can add it with the inventory screen if an audit trail is introduced.
