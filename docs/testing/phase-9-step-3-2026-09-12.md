# Phase 9 step 3 — backups, disaster recovery, monitoring: acceptance record (2026-09-12)

Plan: [docs/plans/phase-9.md](../plans/phase-9.md) step 3 design. Everything below ran on this workstation (Windows 11, Docker Desktop 29.7.2, Git Bash) against the **production compose shape** — `docker compose -p nasmeh -f docker-compose.yml`, never the dev override, so Postgres is not published and the app is the standalone image `nasmeh-app` on port 3000. Deliverables: `scripts/backup.sh`, `scripts/restore.sh`, [docs/RUNBOOK.md](../RUNBOOK.md), process metrics on `/api/health`, log rotation in compose, `tests/unit/health-route.test.ts`.

## Delivered behaviour

- **`scripts/backup.sh [BACKUP_ROOT]`** — `pg_dump --clean --if-exists` of `nasmeh` through the running `db` container, gzipped, plus one `tar.gz` per media volume (`/app/catalog-uploads`, `/app/public/uploads`, `/app/review-uploads`, `/app/support-uploads`) read through the app container's own mounts (`docker run --volumes-from`), into `BACKUP_ROOT/<YYYY-MM-DD_HHMM>/` with a `manifest.txt` (timestamp, image id, applied migrations, order count, sizes, sha256). Retention on every run: newest 14 daily, then Sunday backups for 8 weeks. Each run **verifies its own dump** before the directory counts as a backup (finding F2) and deletes the directory if verification fails.
- **`scripts/restore.sh <backup-dir> [project] [port]`** — brings the backup up as a separate compose project (`nasmeh-restore`, port 3100) from the same image with its own volumes and network: create without starting, start `db`, load the dump with `ON_ERROR_STOP=1`, unpack the four archives into their volumes, start `app`, wait for `/api/health`, then print health, migration and order counts, per-directory file counts and the number of private files found under `public/uploads` (must be 0). Refuses to run if the target project already has containers, or if the backup directory is incomplete.
- **`/api/health`** — adds `uptime`, `memory.rssMb`, `memory.heapUsedMb` and `node` to the existing `status`/`db`, on both the 200 and the 503 branch, with `Cache-Control: no-store`. Two unit tests.
- **Log rotation** — `logging: json-file, max-size 10m, max-file 5` on `app` and `db` through a YAML anchor (at most 50 MB per container).
- **[docs/RUNBOOK.md](../RUNBOOK.md)** — deploy, rollback, backups, restore drill, cron jobs, monitoring (health endpoint, uptime checker with the keyword rule, process metrics, logs), incident table, forced-failure drill. AGENTS.md §6 now points at it.

## Forced-failure and monitoring drill

The runbook's checker rule implemented literally (status 200 **and** the keyword `"db":"up"`, alert after 2 consecutive failures):

```
T0 baseline    UP   code=200 {"status":"ok","db":"up","uptime":7565,...}
               container health: healthy, restart count 0

T1 docker compose -f docker-compose.yml stop db
   check #1    DOWN code=503 {"status":"error","db":"down","uptime":7567,...}
   check #2    DOWN code=503 {"status":"error","db":"down","uptime":7578,...}
   >>> ALERT: 2 consecutive failures — the uptime checker would page

T2 docker compose -f docker-compose.yml start db
   recovered after 1 check: {"status":"ok","db":"up","uptime":7596,...}
   restart count after: 0        # app never restarted; the Prisma pool reconnected
   container health after a HEALTHCHECK interval: healthy
```

`uptime` runs 7565 → 7567 → 7578 → 7596 across the outage: it never resets, which is the evidence the app process survived the database going away and came back without intervention.

The Docker `HEALTHCHECK` was separately proven to flip, on the disposable restored stack (the live reading above was taken before the retries had elapsed, which is why it still said `healthy`):

```
db up      wget -q --tries=1 --spider … ; exit=0
db stopped wget: server returned error: HTTP/1.1 503 Service Unavailable ; exit=1
after interval 30s × retries 3 → container health: unhealthy
health log exit codes: 0 0 1 1 1
```

So the container is marked `unhealthy` ~90 s into an outage while the external checker pages at ~2 min; both are recorded in the runbook. Docker does not restart an unhealthy container — `unless-stopped` acts only when the process exits — so the external checker is the thing that pages a human.

Log rotation is actually applied, not just declared:

```
app: json-file map[max-file:5 max-size:10m]
db:  json-file map[max-file:5 max-size:10m]
```

## Findings fixed during the step

| # | Finding | Fix |
|---|---|---|
| F1 | **Both scripts were unrunnable under Git Bash.** MSYS rewrites container-absolute arguments before they reach docker — `/app/catalog-uploads` arrived as `C:/Program Files/Git/app/catalog-uploads` (verified directly), so every `tar -C`, `find` and `mkdir` in the scripts addressed a path that does not exist in the container | `export MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL="*"` at the top of both scripts, with the reason in a comment. No effect on the Linux host |
| F2 | **A truncated dump would have been recorded as a good backup.** `pg_dump … \| gzip > file` exits with *gzip's* status, so a `pg_dump` killed mid-way (disk full, container going away) left a short `db.sql.gz` behind a zero exit — and the retention loop would eventually rotate the last good backup away | `gunzip -t` plus a check for pg_dump's own `-- PostgreSQL database dump complete` marker; a run that fails removes its directory and exits non-zero. The marker is read from a 20-line window, not the last line: **pg_dump 16.10+ appends a `\unrestrict <token>` trailer after it** (found because the first version of the check, using `tail -3`, rejected a perfectly good 127 kB dump from pg_dump 16.15) |
| F3 | `restore.sh` required only the five archives, so a backup interrupted between the dump and the manifest could be restored as if complete | `manifest.txt` — written last — is required too |
| F4 | **The new `tests/unit/health-route.test.ts` failed** (`Error: connection refused`) while the endpoint itself was correct. `beforeEach(() => mocks.queryRaw.mockReset())` is a concise arrow, so it *returns* the mock; Vitest treats a value returned from a hook as a teardown callback and **called the mock after each test**, where the rejecting implementation threw outside the route's `try`/`catch`. Confirmed by instrumenting: the route returned 503 with the right body and the mock was called exactly once | `beforeEach(() => { mocks.queryRaw.mockReset(); });` with a comment on why the braces matter. The suite has no other occurrence of the pattern (grep) |
| F5 | **`docker-entrypoint.sh` would be checked out non-executable on the Linux host**, and so would the two new scripts: `core.filemode=false` on this Windows workstation and the file was tracked as `100644`. The image's `ENTRYPOINT ["./docker-entrypoint.sh"]` would fail with permission denied on a host-built image, and the runbook's cron line `scripts/backup.sh …` likewise. It works here only because Docker's Windows build context marks files `0755` | `git update-index --chmod=+x docker-entrypoint.sh` and `git add --chmod=+x` for both scripts; all three are now `100755`. Latent since the Dockerfile was written — it would have surfaced as a step 5 deployment failure |

## Deviations from the step 3 design

1. **The drill ran on Windows + Docker Desktop, not on the Linux target.** That is the workstation the plan assigns to this step, and it exposed F1 and F5 — both host-portability defects a Linux-only run would have hidden. What it cannot prove is the cron path itself (`date -d`, `sha256sum`, `logrotate` on the real host); step 5 re-runs `backup.sh` and one restore drill on the server as part of deployment acceptance.
2. **Fixtures were inserted by script**, not placed through the storefront (no order was checked out, no photo uploaded through the review form). The drill proves the backup/restore round trip, not the write paths, which Phases 3–6 cover.
3. **The uptime checker is the documented placeholder**, not an installed product: the alert rule was executed as a shell loop implementing exactly the runbook's rule (200 + `"db":"up"` keyword, 2 consecutive failures). Choosing Uptime Kuma or a hosted checker belongs to step 5 with the host.
4. **The support-uploads fixture is a bare private file** with no `Ticket` row; what it proves is the fourth volume's round trip and that `0600` survives it.

## Operations notes

- `alpine:3.20` is pulled on first use by both scripts (4 s here); on a host without egress, pre-pull it.
- The restored stack reads the **same host `.env`** as the live one, so it comes up with live SMTP and payment credentials — a working store on port 3100, not a sandbox. Recorded in the runbook; never point a scheduler or the proxy at it.
- The restore's `chown -R 1000:1000` matches the `node` user in `node:20-alpine`; if the base image's uid ever changes, that line changes with it.
- Backups are local to the host. Off-host sync (`rclone`/`restic`, which also encrypts the private photos) is a step 5 decision with the host's storage, and is called out in the runbook.
